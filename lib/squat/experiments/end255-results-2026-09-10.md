# Fixed-255 end-column bases — 2026-09-10

The fixed-255 optimization is **marginal for AVX2**: the best version takes
0.3–1.2% less decode time across the final run medians. The eight-byte version
is slower. For SSE2, most of the apparent gain comes from loading and widening
all sixteen bytes together; base 255 contributes only another 1.7–2.7% against
that stronger baseline. Scalar group decoding takes 14–15% more time.

The more promising change is therefore **full-group SSE2 decoding with ordinary
subtraction**, which takes 13–16% less time than the four-byte-load reference.
It requires neither a special base choice nor a base-255 branch and retains the
actual column maximum. I would prioritize that change over adopting fixed-255
bases. These are column microbenchmarks, not end-to-end iterator timings, and
production packing/decoding were not changed by this experiment.

The candidate preserves `end_column = base - u8_delta`. When every live end
column in a group is at most 255, a private copy chooses base 255 and stores
`delta = 255 - end_column`. Other groups retain their original bases and deltas.
At base 255, complementing the byte reconstructs the value; otherwise the
specialized decoder falls back to ordinary subtraction. There are no changed
lane widths, group boundaries, flags, sentinel meanings, or format versions.

Four variants isolate the changes:

- **baseline:** original maximum bases and ordinary subtraction.
- **existing-complement:** original bases, with the special path only when the
  original maximum already equals 255.
- **fixed-subtract:** choose 255 where eligible, but retain ordinary subtraction.
- **fixed-complement:** choose 255 and use the specialized decoder.

The scalar implementation uses `delta ^ 255u`. SIMD versions complement packed
bytes before widening. SSE2 complements a full 16-byte group and widens to four
u32 vectors. AVX2 has two versions: two separate eight-byte loads/complements,
and one 16-byte load/complement followed by two widening operations. Both AVX2
versions share the same ordinary subtract baseline. SSE2 has a four-byte-load
baseline and a full-16-byte-load baseline; the latter isolates the benefit of
base 255 from the benefit of wider loads.

That comparison changes the loading/widening strategy while keeping original
maximum bases and subtraction. It is independent of the fixed-255 policy.
The ratios in different tables should not be divided to infer another median:
each comparison is computed per file first.

The `fixed-subtract` controls are generally close to baseline. Against the
arithmetic control on the *same rebased arrays*, the sixteen-byte AVX2 special
path takes 0.6–2.0% less time, and full-width SSE2 takes 1.7–3.6% less. Those
small gains do not imply the improvement is uniform across files or that the
whole iterator would improve by the same percentage.

Low-eligibility inputs regress. Only 1.4% of the groups in the large minified
TypeScript-parser input qualify; its sixteen-byte AVX2 candidate takes 2.7–6.3%
more time and full-width SSE2 takes 6.7–8.6% more. This is a reason to avoid
adding the check universally on the strength of the small aggregate gains.
Across files, the median eligible fraction is 100% for bounded inputs and
99.86% for large inputs, but individual long-line files are very different.
The median fraction of groups whose original maximum is already 255 is zero.

A preliminary probe showed a large SSE2 improvement even when almost no group
took the special path. Assembly inspection exposed different loop placements,
so the final experiment added explicit alignment and the full-width subtraction
control. The pilot also used a casted byte complement for scalar decoding;
the final source uses XOR with 255 to avoid prescribing an unnecessary
truncation. Only the final six-kernel runs appear in the tables and final JSON.
This code-generation sensitivity is why an apparent 20% SSE2 gain should not be
attributed entirely to fixed-255 bases.

Measurements used the existing benchmark VM, Xeon 2.20 GHz (family 6, model 79),
pinned to CPU 0. GCC 15.3.0 compiled with `-O2 -g`, no LTO, and assertions enabled.
The aligned build additionally used `-falign-functions=64 -falign-loops=32` for
the probe; linked runtime/library objects were identical. Scalar probe functions
disable autovectorization. Baseline and specialized functions are kept separate
with `noipa` so unused stores or repeated calls cannot be optimized away.

Both builds ran both file orders. The execution sequence was default-forward,
aligned-reverse, aligned-forward, default-reverse. Every file/kernel calibrated
batches to at least 4 ms of baseline work and then ran sixteen repeats per
variant, rotating and reversing variant order. Parsing, packing, private-column
construction, and validation were outside the timers. Group decoders wrote all
sixteen physical lanes and consumed a changing live lane for a checksum;
per-node decoding consumed every live value. Absolute per-node and group times
therefore represent different workloads and should not be compared directly.
The reference kernels specialize ordinary end-column subtraction to sixteen
8-bit lanes; these are not calls through the production iterator API.

All 80 final file/build/order cases passed every live-value comparison and
cross-variant checksum check. The final artifact retains all 30,720 timing
samples. ASan/UBSan passed all six kernels and four variants on synthetic cases
covering all 256 byte values, bases 0/255/256 and high-bit bases, partial groups,
and exact final allocations, plus the C representative with an instrumented
runtime/library. The Makefile target and Python syntax check passed. The VM was
returned to its original stopped state after the results were downloaded.
